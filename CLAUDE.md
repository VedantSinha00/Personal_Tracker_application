# Project Standards & Handoff Guide

## 1. Core Principles
- **Sequence:** Always follow `Specify → Plan → Task → Implement`.
- **Deterministic Code:** Provide exact values and hex codes; never use vague goals.
- **Scope:** Define exactly what to touch AND what not to touch in every prompt.

## 2. Structured Communication (XML)
Use these semantic layers for all complex tasks:
- `<technical_context>`: Stack, frameworks, and constraints.
- `<functional_requirements>`: User behavior and acceptance criteria.
- `<integration_details>`: API, state, and edge cases.
- `<verification_protocol>`: Test commands or audit steps.

## 3. Persistent Constraints
- **Always:** Use Red/Green TDD (write tests first).
- **Ask First:** Before adding new dependencies or changing database schemas.
- **Never:** Commit to Git automatically; never bypass safety checks.

Messages distinguish connectivity failures ("can't reach the server") from database policy/schema rejections via `_isNetworkError` (Postgres/PostgREST error codes => server replied). Verified end-to-end in a real browser against the live module pipeline.
- [Habits Data-Loss Fix & Deep-Link Login]: Bumped version to 1.3.9. **Root-caused and fixed the destructive habits sync** that wiped a user's real habits on sign-out→sign-in: sign-out clears the local `wt_habits` cache, the optimistic pre-load `renderAll()` then exposed `DEFAULT_HABITS`, and `_syncHabits`'s old delete-all-then-insert pushed those defaults to the cloud (deleting the real ones). Fix in `storage.js` adds three independent guards: (1) a session **hydration gate** (`_remoteHydrated`, reset at the start of `loadFromSupabase`, set true only on its successful completion) so habits never push before the cloud is loaded into local; (2) `_syncHabits` **re-reads `loadHabits()` at fire-time** instead of trusting the debounce-captured array; (3) a **non-destructive diff** (insert/update/delete-changed via `.in()`, no constraint dependency) plus an anti-wipe guard. `loadFromSupabase` also cancels any habits push queued by the optimistic render. **Deep-link login fix** in `main.js`: register `app.setAsDefaultProtocolClient('weekly-tracker')` (dev vs packaged branch) so the OAuth callback can return to the app — previously Windows showed "no app associated" and login could never complete after logout. SEC-05 login path now testable on this build (sign out → back in).
- [Carry-Forward Hydration Fix]: Bumped version to 1.3.11. **Root-caused and fixed the broken weekly carry-forward.** `carryForward()` (`stack.js`) reads last week's data only from the local `wt_wk_<N-1>` cache, but `loadFromSupabase()`'s week-boundary guard refused to hydrate `stack`/`todos` for any non-current week (falling back to the local copy). On a fresh session / new device / post-sign-out cache clear, last week wasn't cached locally, so the cloud's real data was dropped AND the key was rewritten empty — stamped with the remote `updated_at`, making the strict-newer timestamp guard skip it on every later load (sticky poison). Because `loadFromSupabase()` runs before the rollover's `carryForward()`, the carry saw an empty source and silently did nothing. Fix in `storage.js`: (1) `localHasNoStackTodos` — when local holds no stack/todos there are no edits to protect, so remote stack/todos are hydrated (the flag flips false the instant any local content exists, preserving the original anti-clobber protection); (2) a `needsBackfill` self-heal that bypasses the timestamp tie for a past/future week whose local cache is empty but whose cloud row has content, recovering previously-poisoned records. Hydration still uses raw `localStorage.setItem` (never `save()`), so cloud data was never overwritten and remains recoverable.
- [Update Resilience]: Bumped version to 1.3.10. Decoupled the auto-update UI from authentication. `initUpdateListeners()` (the "Update Ready / Restart" toast + restart wiring in `app.js`) was previously only called inside `handleAuthReady()`, so a user who couldn't sign in never saw the update prompt — a login-breaking release could strand them with no path forward. Now wired once at module-scope bootstrap (guarded by `_updaterInitialized`, so the existing post-auth call is a safe no-op). The main-process updater in `main.js` already downloaded regardless of auth; this surfaces the prompt on the login screen too (the `toast.js` container is created at module load, so it renders pre-login). Net effect: updates can always be received AND applied, even from a locked-out state.
- [Task ID Fix]: Bumped version to 1.3.13. Assigned unique task IDs (UUID) to tasks created from the Overview tab, and enabled runStartupMigration to execute on app start and loadFromSupabase. This ensures all tasks have unique IDs and resolves bugs where checking off tasks or pushing tasks to backlog failed in the Stack tab.
- [Modal Error Fixes]: Bumped version to 1.3.14. Fixed stale `stError` in the stopwatch modal — "Please select an area first." persisted on screen after the user subsequently picked a category, because the `stCat` change listener never cleared it. Fixed by adding `hideModalError('stError')` to that listener. Also removed dead `hideModalError('fError')` call from `openM` — `fError` was never written to anywhere in the codebase.
- [Carry-Forward Hydration Hole #2]: Bumped version to 1.3.15. **Root-caused and fixed the recurring "last week's pending todos don't carry" bug.** In `loadFromSupabase()` (`storage.js`), past-week stack/todos hydration was gated by `allowTodosStack = rowIsCurrentWeek || !!row.__carried_forward || localHasNoStackTodos`. The middle clause was **dead**: `__carried_forward` is a local-only marker (stripped from caches by the migration at lines 874-887, never written to the `weekly_data` table by `_perfSyncWeek`), so `row.__carried_forward` from a cloud fetch is **always `undefined`**. That left only two ways for the cloud to win on a past week: it's the current week, or local is empty. The hole: when last week's local cache holds **stale** stack/todos (e.g. an empty/partial edit from another device synced a newer `updated_at`, or a prior poisoned write), the cloud's real pending todos were **discarded** and the record re-stamped with the cloud timestamp — making the stale local todos sticky-authoritative, so `carryForward()` (which reads `wt_wk_<N-1>` from localStorage) found nothing to carry. The existing `needsBackfill` self-heal only covered the *empty*-local case. **Fix:** replaced the dead clause with `cloudStrictlyNewer = !!localTs && new Date(row.updated_at) > new Date(localTs)`. Reaching that line already proves the cloud should win — the `staleByTimestamp` guard above returns early (and pushes local up) whenever local is newer or ties — so a strictly-newer cloud `updated_at` means the cloud holds the more recent genuine edits and its stack/todos may overwrite. `localHasNoStackTodos` still covers the timestamp-tie poisoned-record case. This self-heals previously-poisoned records on next load (no terminal command needed). The manual terminal fix the user ran previously was a workaround for exactly this hole (re-stamping or clearing `wt_wk_<lastweek>` so the empty-local self-heal would fire).

- [Carry-Forward Auto-Trigger Backstop]: Bumped version to 1.3.16. **Root-caused the *real* recurring "last week's pending todos don't carry" symptom — it was never a data-loss bug.** Diagnosed live: last week's todos were intact in BOTH cloud and local cache; carry-forward simply never *ran*. Cause: the auto-carry is driven solely by the single-shot `wt:week-changed` event, which `checkForWeekChange()` (`weekState.js`) stamps `wt_last_monday` for the moment it dispatches. If that rollover is consumed before `carryForward()` completes — early reload, second app instance, or a throw in the `renderAll()`/`runStartupMigration()` chain that precedes the `carryForward()` call in the `wt:week-changed` listener (`app.js`) — the week is marked "handled" permanently: `thisMon === wt_last_monday` makes `checkForWeekChange()` early-return on every later launch, so the event never re-fires and carry never gets a second chance. Compounded by a **dead manual fallback**: the "↩ Carry from last week" button (`carryBtn`) is referenced in `stack.js` but exists in NO HTML file, so users have no way to invoke carry manually — leaving the console as the only recovery path. **Fix:** added `ensureCarryForward()` in `app.js`, an idempotent startup backstop called after `checkForWeekChange()` (and the event listener now stamps the same flag). It runs on EVERY launch independent of the rollover event, triggers `carryForward()` at most once per week (tracked by a new `wt_last_carry` = current-week-offset flag), and only when the current week is genuinely empty of stack/todos. Safe to re-run because `carryForward()` only fills empty fields and dedups by text. This removes the dependency on a one-shot event ever firing at exactly the right time.
